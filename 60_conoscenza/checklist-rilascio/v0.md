# Checklist di sicurezza pre-rilascio — v0

Uso: da compilare identica per **ogni Consegna verso un ambiente pubblico**,
di ogni commessa. Ogni voce è binaria (sì/no). Se anche una sola voce

## 1. OWASP Top 10 (2021) — controlli minimi

### A01 — Controllo degli accessi
- [ ] Ogni endpoint/route che restituisce o modifica dati verifica
      l'autorizzazione lato server (non solo lato client/UI).
- [ ] Nessun endpoint espone dati di un utente ad un altro utente autenticato
      cambiando solo un ID nella richiesta (test IDOR eseguito manualmente su
      almeno gli endpoint CRUD principali).
- [ ] Le route amministrative sono separate e verificano un ruolo, non solo
      l'autenticazione.
- [ ] CORS configurato con whitelist esplicita di origini, non `*` in
      produzione.

### A02 — Fallimenti crittografici
- [ ] Tutto il traffico pubblico è servito solo su HTTPS (redirect HTTP→HTTPS
      attivo, verificato con richiesta reale).
- [ ] Nessuna password, token o dato personale sensibile è salvato in chiaro
      nel database (hash con algoritmo adeguato per le password, es.
      bcrypt/argon2).
- [ ] Cookie di sessione hanno `Secure`, `HttpOnly`, `SameSite` impostati.
- [ ] Nessuna chiave/certificato scaduto o self-signed in produzione.

### A03 — Injection
- [ ] Tutte le query al database usano parametrizzazione/ORM, nessuna
      concatenazione di stringhe con input utente.
- [ ] Ogni input utente che finisce in HTML è sottoposto a escaping/sanitizzazione
      (verifica XSS su almeno un campo di testo libero per form).
- [ ] Se sono presenti comandi di sistema o query dinamiche, l'input utente
      non raggiunge mai direttamente uno shell/eval. **[N/A ammesso]** se
      l'app non esegue comandi di sistema.

### A04 — Design insicuro
- [ ] Esiste un limite di rate (rate limiting) su login, registrazione e
      reset password.
- [ ] I flussi che toccano soldi o dati sensibili hanno una conferma
      esplicita lato server, non solo uno stato lato client.

### A05 — Configurazione errata della sicurezza
- [ ] Nessuna pagina di debug, stack trace dettagliato o console admin
      raggiungibile pubblicamente in produzione.
- [ ] Header di sicurezza presenti: `Content-Security-Policy`,
      `X-Content-Type-Options: nosniff`, `X-Frame-Options` (o equivalente
      CSP frame-ancestors).
- [ ] Nessuna credenziale o configurazione di default (es. admin/admin) attiva.
- [ ] Directory listing disattivato sul server/storage pubblico.

### A06 — Componenti vulnerabili e obsoleti
- [ ] Scansione delle dipendenze eseguita (es. `npm audit`, `pip-audit`,
      Dependabot) e nessuna vulnerabilità di severità alta/critica aperta
      senza mitigazione documentata.
- [ ] Versione del framework/linguaggio principale è una versione ancora
      supportata (non end-of-life).

### A07 — Fallimenti di identificazione e autenticazione
- [ ] Password: lunghezza minima enforced lato server, nessun limite massimo
      assurdamente basso.
- [ ] Sessioni scadono dopo un periodo di inattività definito.
- [ ] Logout invalida la sessione lato server, non solo lato client.
- [ ] Se previsto login con provider esterni (OAuth), i token non sono
      esposti nell'URL o in log persistenti.

### A08 — Fallimenti di integrità di software e dati
- [ ] Le dipendenze sono installate da lockfile (`package-lock.json`,
      `poetry.lock`, ecc.), non da range di versione aperti in produzione.
- [ ] Pipeline di CI/CD non permette merge/deploy senza revisione se più di
      un mandato tecnico è coinvolto nella commessa. **[N/A ammesso]** se un
      solo sviluppatore lavora sulla commessa.

### A09 — Fallimenti di logging e monitoraggio
- [ ] Esiste un log applicativo per eventi di sicurezza (login falliti,
      errori 5xx, accessi negati) consultabile senza accesso diretto al
      server di produzione.
- [ ] Nessun dato personale o segreto (password, token, numeri di carta) è
      scritto in chiaro nei log.
- [ ] È attivo almeno un canale di allerta per errori critici in produzione
      (es. notifica su errore 5xx ricorrente).

### A10 — Server-Side Request Forgery (SSRF)
- [ ] Se l'app effettua richieste HTTP verso URL fornite dall'utente (webhook,
      import da URL, fetch immagini remote), gli URL sono validati contro una
      whitelist o comunque non possono raggiungere IP interni/privati.
      **[N/A ammesso]** se l'app non effettua richieste server-side verso URL
      fornite da utenti.

## 2. Gestione segreti (CLAUDE.md §6)

- [ ] Nessun segreto (chiave API, password DB, token) è presente nel codice
      versionato o nella cronologia git (verificato, non solo dichiarato).
- [ ] I segreti sono iniettati via variabili d'ambiente o secret manager,
      distinti per ambiente (sviluppo/staging/produzione).
- [ ] I segreti di produzione non sono mai gli stessi usati in sviluppo/staging.
- [ ] L'accesso ai segreti di produzione è limitato a chi ne ha effettiva
      necessità operativa (non l'intero team ha le credenziali del DB
      produzione).
- [ ] Esiste una procedura documentata di rotazione dei segreti in caso di
      sospetta compromissione.

## 3. Backup verificati (non solo configurati)

- [ ] Esiste un backup automatico del database di produzione, con frequenza
      dichiarata e coerente con il rischio di perdita dati accettabile dal
      committente.
- [ ] **Il backup è stato ripristinato almeno una volta in un ambiente di
      prova** e il ripristino ha prodotto dati coerenti e utilizzabili — non
      basta che il job di backup risulti "eseguito con successo" nei log.
      Data dell'ultimo test di ripristino: ______________________
- [ ] I backup sono conservati in una posizione diversa dall'infrastruttura
      primaria (non lo stesso disco/server dei dati live).
- [ ] I backup contenenti dati personali seguono la stessa policy di
      sicurezza dei dati live (cifrati a riposo, accesso limitato).

## 4. Piano di rollback scritto

- [ ] Esiste un documento scritto (non solo un'intenzione verbale) che
      descrive come tornare alla versione precedente in caso di rilascio
      fallito, incluso: comando/procedura esatta, tempo stimato, chi è
      autorizzato ad eseguirlo.
- [ ] Il piano di rollback copre anche le migrazioni di schema database
      (come si torna indietro se la nuova versione ha modificato lo schema),
      non solo il codice applicativo.
- [ ] Il piano di rollback è stato controllato per l'ultima volta il:
      ______________________ (data), non solo scritto una volta e mai
      rivisto.
